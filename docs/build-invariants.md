# Build & Release Invariants

**Last updated**: 2026-07-14

This doc covers **build-artifact-level** invariants — properties of the compiled `main.js` bundle and the version-tracking files, checked mechanically by `npm run verify:build` (`scripts/verify-build.mjs`), which runs after every `build`/`build:quick`.

For **source-level lint rules** the Obsidian community review bot scans (sentence-case, no `eslint-disable` on certain rules, etc), see [docs/obsidian-review-bot.md](obsidian-review-bot.md) instead — a different layer of compliance, checked by `npm run lint`, not this gate.

## The invariants

| Invariant | Why it exists | What breaks if violated | Learned in | Automated by |
|---|---|---|---|---|
| `minAppVersion` covers every Obsidian API actually used | The plugin uses `SecretStorage`, a v1.11.4 API; an older `minAppVersion` lets the plugin install on a version where that API doesn't exist | Runtime crash on older Obsidian installs; also a blocking Obsidian review-bot error (`no-unsupported-api`) | `5f402f7` | `npm run lint` (`obsidianmd/no-unsupported-api`, already enforced — not new in this gate) |
| No remote `<script>` injection (CDN loaders) reintroduced | D3 was previously CDN-loaded in `TagNetworkView`; `heic2any` was previously CDN-loaded in `imageProcessorService`. Both were bundled as submodules instead | Obsidian's review bot blocks "dynamic script injection (remote code)" as an Error, not a warning — a submitted release would be rejected | `5f402f7` | Document-only (a code-review judgement call — see `checkSetImmediatePolyfillNeutralised` below for the one *mechanically* checkable sub-case) |
| The dead `setImmediate` `<script>` polyfill (bundled via `jszip`/`pptxgenjs`/`docx`/`dom-to-pptx`) stays neutralised in the output bundle | `esbuild.config.mjs`'s `neutralizeSetImmediateScriptPolyfill` plugin rewrites the polyfill's `createElement("script")` calls to `createElement("span")` on every build, so the review bot's script-injection heuristic doesn't fire on a pattern that is dead code in Electron anyway | If the esbuild plugin regresses (a dependency update changes the polyfill's shape, or the plugin itself breaks), the literal reappears in `main.js` and the next release is rejected by the review bot | `7f6966a` | `checkSetImmediatePolyfillNeutralised()` — uses the shared `scripts/setImmediatePolyfillSignature.mjs` predicate, the same one the esbuild plugin itself uses |
| The bundle contains zero `"manifest.json"` string literals | The review bot's self-update heuristic ("overwrites its own files by extracting an archive") fires on the combination of bundled `jszip` + vault file writes + the literal string `manifest.json` anywhere in the bundle. The plugin legitimately bundles `jszip` (officeparser/xlsx) and writes vault files, so the ONE thing kept out of the bundle is the literal | Reintroducing a `"manifest.json"` string (e.g. a new feature that reads/writes a file with that exact name) trips the same false-positive self-update Error | `3bae157` | `checkNoManifestJsonLiteral()` |
| `package.json.version === manifest.json.version`; `versions.json` contains a key equal to that version mapped to `manifest.json.minAppVersion` | Obsidian's release process reads `manifest.json.version` to identify the release and `versions.json` to know the minimum app version each historical release required. A mismatch breaks the update mechanism for users on old Obsidian versions | A future release could ship with an out-of-sync `manifest.json`/`versions.json`, silently breaking update compatibility checks for some users | Corrected during planning — `versions.json` was mis-described in an earlier draft of this invariant as "all three files hold an equal version string"; it is actually a version→minAppVersion history map | `checkVersionSync()` — validates the **current** release's three-way agreement (with presence/type checks so an empty/malformed file can't pass via `undefined === undefined`). **Does not and cannot verify that historical `versions.json` entries were preserved** — a single artifact snapshot has no way to know what a *prior* snapshot contained. Preservation of history is a property of `version-bump.mjs`'s own upsert logic (never overwrites, only adds a key), not something this post-hoc gate can independently confirm. If that guarantee ever needs enforcing at the gate level, it would require diffing against the previous release's `versions.json` (e.g. via git), which is out of scope for this pass. |
| Bundle size (currently ~7.0 MB) | Disclosed, accepted trade-off (single-file bundle + local ONNX embeddings + the full export suite) | N/A — this is informational, not a pass/fail gate. A silently *growing* bundle is worth knowing about even though no specific threshold is enforced | N/A | `reportBundleSize()` — **info only, never fails** |

## Not automated (and why)

- **`fs`/`child_process` usage** (FFmpeg, desktop-gated via `desktopRequire`), **`eval`/`new Function`** (bundled-dependency polyfills, not plugin code), **transitive vulnerable dependencies** (xlsx/jspdf/dompurify/@xmldom/protobufjs/ws) — these are already-disclosed, judgement-based acceptances of known Obsidian review-bot *warnings* (not blocking errors). A mechanical check here would just restate today's known-warning count as a magic number with no actionable failure mode, and would need manual updating every time a new disclosed warning is accepted — busywork masquerading as automation.
- **General "no remote script injection" policy** — the specific, currently-known instances (D3 CDN, `heic2any` CDN, the setImmediate polyfill) are each addressed above. A generic allowlist/denylist engine for arbitrary future script-loading patterns is not worth building until a second, differently-shaped instance is actually discovered.

## Where the gate runs

The checks run **inside `esbuild.config.mjs`'s production build path**, immediately after the bundle is written and **before** the local auto-deploy step (which copies `main.js`/`manifest.json`/`styles.css` to the vault/mobile staging folders) — so a failing gate means the artifact never reaches those folders in the first place, not just that the terminal shows a red exit code afterward (an ordering bug caught during implementation-audit: an earlier draft chained the checks as a separate `npm run verify:build` step *after* the whole build+deploy script had already run). This applies only to `production` builds (`npm run build` / `npm run build:quick`) — **not** `npm run dev` (watch mode, unminified iteration builds, not release candidates).

`.github/workflows/release.yml` already calls `build:quick` on every tag push, so the gate is wired into the release path with zero changes to that workflow — a failing check calls `process.exit(1)` before deploy, which fails the `node esbuild.config.mjs production` step and therefore the whole CI job.

`npm run verify:build` also remains available as a **standalone** command — useful to check an already-built `main.js` without rebuilding (e.g. after manually editing a config).

A passing run prints every check it ran (pass/fail/info) so "what did this actually verify" is always answerable from the gate's own output, not from reading the script source.
