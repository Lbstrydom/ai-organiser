# Inbox Sweep and Google Tasks Export

Reads the notes in the folders you choose and proposes next actions, waiting-for items, projects and someday items. You review every item first; only what you approve is added to one sweep report note, and your source notes are never changed. Optional: send the approved tasks to one Google Tasks list through your own Apps Script. Both are default off (`inbox-sweep`, stage Refine, requires a provider; `google-tasks-export`, external-account boundary, requires `inbox-sweep`) and byte-identical when off.

> **Capture inbox.** The [capture inbox](capture-inbox.md) is the Clarify step before this sweep. It reads the same inbox folders and keep-out rules (one inbox, one privacy policy), keeps captures it still holds out of the sweep (`sweepRunPolicy`), and leaves tasks to this sweep. Its keep-out and inbox-folder wizard steps are shared code (`ui/setup/inboxScopeSteps.ts`).

## What the user does

`Set up inbox sweep` (three steps: inbox folders and the report note; **what to keep out**, which is required; a preview that counts notes without contacting any AI provider). Then `Sweep inbox`: a confirmation with the number of notes and characters (plus a once-per-session notice when the provider is a cloud service), a review window where every item starts unchecked, and **Add N to sweep report**. `Set up Google Tasks` is three steps too: connect a setup script, pick a list, then lock the script to that list.

## Pipeline

| Stage | File | Notes |
|---|---|---|
| Snapshot | `services/inboxSweep/noteSnapshot.ts` | Each note is read once. Tags and properties are parsed from the same bytes, never from the metadata cache. |
| Guard | `services/inboxSweep/sweepGuard.ts` | Pure and fail-closed, runs before any model call on the full text. Excludes by folder, protected folder, tag (nested too), `key: value` property, term, or anything unknown (unreadable frontmatter, too large, not a string). Only it can produce a `GuardedSnapshot`, which is all the prompt builder accepts. The policy revision is re-checked immediately before every call. Ships no built-in company, folder or term. |
| Extraction | `services/prompts/sweepPrompts.ts`, `inboxSweep/sweepService.ts` | XML-structured prompt returning the minutes `gtd_processing` shape with an `evidence` quote per item. Evidence not found in the note drops the item. The schema degrades: text is truncated, unknown contexts become empty, malformed items are dropped and counted. |
| Review | `ui/modals/InboxSweepReviewModal.ts` | Unchecked by default; edit text and context; per-note "mark as swept". Footer reads "Add N to sweep report", or "Mark reviewed" when none are ticked. |
| Outbox | `inboxSweep/sweepCommit.ts`, `sweepLedger.ts` | Order: persist the approval record, write the report section, mark items reported and apply the dispositions, then export. Each step is repeatable; recovery reads the report note and compares the ids it holds with the record. |
| Report | `inboxSweep/sweepReport.ts` | Owned `<!-- aio:sweep run=... -->` sections. Task text is inline data only: newlines and control characters collapse, comment delimiters and `[[ ]]` are neutralised, text is capped, the context is restricted to the known `@` set. A damaged or partial section is a conflict that writes nothing. |
| Tasks script | `inboxSweep/tasksScriptTemplate.ts` | Setup deployment (no list approved: cannot create anything) then operational deployment (locked to one list id, enforced in the script). Script lock, at most 25 items per request, a four minute budget, `[aio:<id>]` markers in task notes so a retry never duplicates. |
| Export | `inboxSweep/tasksExportService.ts` | Only `reported` items, in batches of 25, over the shared Apps Script client. The guard is re-run on each item's current source note first. One way: completion is never read back. |

## Invariants

- Excluded text never reaches the provider; a test spies on the model call.
- A note is offered again only when its content hash changed. Ledger keys follow renames (`rename` listener in `inboxSweepCommands.ts`).
- **The same item is never added twice.** When a changed note is read again every item in it is proposed again, so each approved item carries identity keys (`itemKeys` in `sweepItemIdentity.ts`: the quoted line and the wording, normalised, one pair for the model's wording and one for the user's edit) remembered per source note (`sweepReportedItems`, at most 500 keys per note, written in the same save as the ledger, moved by the rename listener; tasks recorded by 1.1.1 or earlier are recognised from their stored text, and a task whose export failed still counts because it is in the report). `reportedMatch` has two outcomes. **Exact** (same wording): the review shows the item disabled as "Already in your sweep report", and `commitReview` drops it (and repeats inside a batch, and keyless tasks judged by their text) before anything is persisted, so neither the report nor the Google Tasks export can receive it twice. **Similar** (same quoted line, wording overlapping by at least half): probably the model's rewording, but a sentence can hold two commitments ("Send the invoice to Alice and to Bob"), so the item stays addable with the note "Looks like one you already added" and the user decides. A note with nothing new defaults to "swept". Limits: matching is per note (the same task in two notes is two items), and a task deleted from the report by hand is still treated as added.
- Source notes are never modified. The report note is written with `applyNoteEdit` (no review modal because the review window is the gate), created only after `validateReportPath` and a writability check.
- A failure after the approval record is saved leaves it saved: the next sweep or "Send approved tasks" finishes the record before doing anything else.
- No keep-out rule and no explicit "Nothing to keep out" means no sweep (`sweep-keepout-required`).

- **Rewording and headings.** Close but not identical wording under a different quoted line (the user reworded the line in the note) is `similar`, not new (identical wording stays `exact` whatever the quote): still addable, with the "Looks like one you already added" note. A second report section on the same day is numbered ("Sweep 2026-10-25 (2)") so headings stay distinct; findSection accepts the numbered form and appending stays idempotent.

## Contexts

The `@` contexts the sweep offers for next actions come from one pure module (`inboxSweep/sweepContexts.ts`). The setting `sweepContexts` is the user's own list (one per line in Advanced, at most 12, each `@` plus lower-case letters, digits, `-` or `_`); **`[]` means the built-in set** (`VALID_GTD_CONTEXTS`, imported, never copied, so meeting minutes are untouched). The defaults are never written into settings, so a later change of the built-in set reaches everyone who never customised it, and an unconfigured vault is byte-identical (prompt, parser, report line, dropdown, Google title, stored record; pinned in `tests/sweepContexts.test.ts`). One immutable set per run: `runSweep` reads it once and the prompt, the parser, the review dropdown and the approval all follow that set. An approval made under a custom set stamps it on each task (`ApprovedTask.contexts`); the report line and the Google title judge the context against that snapshot, and a record made under the built-in set carries no such key.

## Lists, routing, dates and completion read-back

Opt-in on top of the one-list export; with the defaults (`tasksLists: []`, `tasksRoutingRules: []`, a main list that needs no date, `tasksReadBack` off) the review, the record, the wire body and the script text are exactly what they were (pinned).

- **Lists.** `tasksListId` stays the one authority for which list is main. `tasksLists` (at most 8) holds the other lists and the main list's title and **needs a date** flag. `resolveTasksLists` is the only reader (it reconciles on every read, so an older plugin changing `tasksListId` just makes another list main) and `updateTasksLists` the only writer (`inboxSweep/tasksRouting.ts`). Lists are chosen from the user's real Google lists (Settings -> Google Tasks -> Your lists), never typed as ids.
- **Rules** (`tasksRoutingRules`): data, first match wins (kind, optional context), then "everything else -> main list". They only **pre-select** a destination in the review; the person's approval is the gate. The agenda destination is not offered yet.
- **Review.** When there is something to choose (another list, a dated main list or any rule) each row gets a destination and, for a list that needs a date, a date input. The row cannot be ticked until a valid date is picked; one unambiguous ISO date in the item's text only **pre-fills** it ("from the text"). Changing the destination drops a date the new list does not need (`inboxSweep/reviewRouting.ts`, pure).
- **The record.** A task approved with routing carries `routingMode: 'routed'`, `kind`, `destination`, `due`, `needsDateAtApproval` and is created **`routed`** (or `kept` for report-only), a state an older plugin never exports or promotes, so it can never be sent undated or to the wrong list by one (a test runs the previous `exportable` against a routed record at every checkpoint). It stays `routed` through every retryable outcome; only a confirmed result moves it, `conflict` and `target-conflict` are terminal. The target list and the exact payload are **frozen and saved before the first request**, and every retry, crash replay and post-redeploy send replays them unchanged. A legacy task is created, serialised and promoted exactly as before. The settings migration keeps every new field and now accepts the new states (a record holding one is never dropped).
- **Export** (`exportApproved` with `routing`): tasks are decided by `decideExport` (complete, send, hold, not-sent, agenda), grouped by target list, in batches of 25 per list. A list the deployed script does not approve is **held**, never replaced by another list: an older script asks for a redeploy (`tasks-script-lists-outdated`), a newer one says the list is not approved; a dated list with no valid date is held (`tasks-due-missing`). Every hold is named in the notice with what to do, and main-list items keep flowing. `due` is sent only for a list that needs a date, as `YYYY-MM-DD` (the script writes it as a date; Google keeps the date only). Without `routing` (a plain one-list setup) the export is the unchanged legacy path with no extra request.
- **Script v2** (`googleScript/googleScriptBuilder.ts`, the `tasks` module): several approved lists (`APPROVED_LIST_IDS`, each request names one and the script rejects any other before touching Google), an export binding (`bind:<exportId>` under the script lock, so two devices that froze different lists cannot both create the task: the second gets `target-conflict` with the original receipt; a v1 `x:` receipt counts as the binding), and the read-only `status` operation. `ping` keeps every v1 field and adds `approvedListIds`, `listsHash` and `capabilities`. The plugin emits the **exact v1 text** unless a v2 capability is wanted (more than one list, or completion read-back), chosen by capability, never by list count alone (`tasksScriptSelect.ts`; v1 is pinned byte for byte by stored copies in `tests/fixtures`). A list that needs a date works on v1 (its upsert already writes `due`), so that alone never forces a redeploy. `classifyTasksScript` gains `lists-outdated`.
- **Completion read-back** (opt-in `tasksReadBack`, command **Refresh task status**): read-only. For tasks the plugin exported the script answers from its **own receipt** (a supplied task id is ignored; an id with no receipt or a different list is `unknown-receipt`), in batches of at most 100 inside a 60 second budget. `remoteStatus` and `checkedAt` change only on `ok` or `not-found`; on any failure the previous observation is kept, and an observation older than 7 days is unknown. Without the `status` capability only this is unavailable (`script-capability-missing`); export keeps working. The plugin never edits, re-dates or completes a Google task.
- **Note link** (opt-in `tasksIncludeNoteLink`): adds one `obsidian://open` line to each task's notes, which puts the vault name and the note path into the user's own Google account; the settings say so.
- **Operation summaries.** Each approval's export writes a `sweep-export` summary through the operation index (running, done or needs attention), reconciled in memory with the approval record, best effort (an index failure never changes an export). The first export with Google Tasks on creates the plugin's `operations/` folder.
- Tests: `tasksRouting`, `tasksRoutedExport`, `googleScriptBuilder` (v2 run against a fake Tasks service: lists, binding, status, forged tuples), `projectIdentity` and `operationsAndScriptCapabilities` for the shared parts.

## Google Tasks setup and the combined script (persona S1 fixes)

- **One copy per deployment kind.** `pingTasksScript` and `normaliseModulePing` report `combined` when the answer carries a `modules` block. The Tasks wizard learns it from Test connection / Test again (`verify`) and then copies the combined script (`copyCombinedScript(plugin, mainListId)`, the chosen-but-unsaved list goes first) instead of the standalone one; until a test ran it copies the standalone script, says so, and offers "Copy combined script instead". Never instruct pasting the standalone script over a combined deployment. The Integrations row says which command to use when a combined script lacks a capability.
- **Finish says why.** The wizard blocks Finish until a check passed and shows a wizard-specific guidance code (`tasks-wizard-unchecked`, `-setup`, `-wrong-list`, `-no-list`) rather than "open the setup" from inside the setup. External checks stay actions, not validation gates.
- **Names, not ids.** `resolveTasksLists` shows the saved `tasksListName` for the main list when its entry has no title.
- **PARA roots are kept** even when a line says an inbox root is not yet an inbox folder; the folder rows use the shared folder picker.

## AI hand-back notes are skipped

A note with a `## Handoff` section (outside code), an `aio:handoff` marker or `aio-handback: true` is left out of the sweep (`looksLikeHandback`), so its Decisions, Questions and Deliverables lines do not come back as tasks; it has its own review (Review AI hand-back). The run says how many were left out. The guard itself is unchanged, because the hand-back review sends a hand-back's next actions through the sweep with that note as their source.
